## 定义

::section{#definition slot="knowledge.definition"}

**数据库并发控制**是一组协调多个事务对共享数据访问的机制，目标是让重叠执行的事务保持隔离性和数据库一致性，并使并发调度等价于某个串行调度。

串行执行按先后顺序逐个完成事务，并发执行允许不同事务的执行区间重叠。并发能够增加单位时间完成的事务数量，并减少事务从提交到完成所需的平均响应时间。

并发执行不等于并行执行。并行执行要求多个处理单元在同一时刻真正执行不同任务；单处理器环境中的并发主要通过交替调度实现。并发若不受控制，会破坏事务隔离性和数据一致性。

## 并发异常示例

::section{#examples slot="knowledge.examples"}

- **丢失更新**：两个事务读取同一旧值并分别修改，后提交的事务覆盖前一个事务的结果。
- **脏读**：一个事务读到另一个事务尚未提交的数据，而该事务随后回滚。
- **不可重复读**：同一事务两次读取同一行，中间另一事务更新并提交，导致两次结果不同。
- **幻读**：同一范围查询在两次执行之间因其他事务插入或删除满足条件的行而得到不同行集合。

## 锁的类型与粒度

**排他锁（X锁）**：用于修改。持有X锁时，其他事务不能同时对同一对象加X锁或S锁。

**共享锁（S锁）**：用于读取。多个事务可以同时持有S锁，但只要仍有S锁，其他事务不能取得X锁。

锁的粒度常见为表级和行级：

- 表级锁管理开销小、加锁快，通常不会因表锁等待形成死锁，但冲突概率高、并发程度低。
- 行级锁管理开销大、加锁慢，冲突概率低、并发程度高，但多个事务竞争不同行后仍可能形成死锁。

InnoDB支持行级锁和表级锁，实际执行时还会使用意向锁等内部锁类型表示加锁意图。

MySQL可显式请求行锁：

```sql
SELECT *
FROM account
WHERE account_no = 'A'
FOR SHARE;

SELECT *
FROM account
WHERE account_no = 'A'
FOR UPDATE;
```

`FOR SHARE`请求共享锁，`FOR UPDATE`请求排他锁；事务提交或回滚后，行锁自动释放。`lock_wait_timeout`控制表级锁等待时间，`innodb_lock_wait_timeout`控制InnoDB行级锁等待时间。等待超时通常返回错误，但不会自动回滚整个事务。

## 三级封锁协议

::section{#protocols}

- **一级封锁协议**：修改前必须加X锁，并保持到事务结束。它防止丢失更新。
- **二级封锁协议**：在一级基础上，读取前加S锁，读完可以立即释放。它进一步防止脏读。
- **三级封锁协议**：在一级基础上，读取前加S锁并保持到事务结束。它进一步防止不可重复读。

三级封锁协议逐步提高隔离性。它们规定读写时锁的持有时间，不直接保证所有并发调度都可串行化。

## 两阶段封锁

::section{#two-phase-locking}

两阶段封锁协议包含：

1. **增长阶段**：可以获得锁，不能释放锁。
2. **收缩阶段**：可以释放锁，不能再获得新锁。

若所有事务遵守两阶段封锁，则它们的并发调度可串行化。两阶段封锁是保证可串行性的充分条件，并非必要条件。

两阶段封锁和三级封锁协议关注不同目标：前者约束锁获取、释放的阶段，后者规定读写锁的粒度与持续时间。严格两阶段封锁通常要求X锁和S锁都保持到事务结束。

## 死锁与活锁

::section{#deadlock}

死锁发生需要互斥、不可抢占、部分分配和循环等待。事务依赖图出现环时，系统可以检测到死锁，并撤销代价较小的事务来打破等待。

```mermaid
flowchart LR
  t1[事务T1] -->|等待R2| t2[事务T2]
  t2 -->|等待R1| t1
```

预防死锁可以在事务开始前一次锁定全部对象，或规定统一加锁顺序。这些方法会增加等待、降低并发，并且难以预知动态访问的对象。

活锁是一个事务长期得不到所需锁，而其他事务不断取得该锁。先来先服务或公平排队可以避免长期饥饿。

## 隔离级别

::section{#isolation}

SQL标准定义四个隔离级别：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 可能 | 可能 | 可能 |
| `READ COMMITTED` | 避免 | 可能 | 可能 |
| `REPEATABLE READ` | 避免 | 避免 | 标准允许 |
| `SERIALIZABLE` | 避免 | 避免 | 避免 |

具体DBMS可能使用多版本并发控制、间隙锁或快照实现更严格的行为。例如InnoDB默认`REPEATABLE READ`，通常通过一致性读和`next-key locking`处理许多幻读场景，但实现细节不等同于SQL标准本身。

```sql
SET SESSION TRANSACTION ISOLATION LEVEL
REPEATABLE READ;
```
